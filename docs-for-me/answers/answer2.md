# Toss POS 연동 및 네이버 지도 크롤러 결합 구현 계획서

이 문서는 Toss POS 단말기를 사용하는 매장의 정보를 최초 연동하고, 네이버 지도 크롤러를 활용해 매장의 상세 메타정보를 자동으로 완성하며, 추후 Toss POS의 통계 자료를 배치(Batch)로 수집하는 전체 아키텍처 및 구현 계획을 정리한 문서입니다.

---

## 1. 전체 아키텍처 개요

현재 시스템은 크게 **Spring Boot (메인 백엔드)**와 **FastAPI (크롤러 전용 마이크로서비스)**로 분리되어 있습니다.

*   **Spring Boot (BE)**: 회원 관리, 온보딩(TV 코드 페어링), DB 저장, Toss OpenAPI 통신, 배치 처리(Batch) 등 메인 비즈니스 로직 담당
*   **FastAPI (Crawler)**: `naver_map_menu_hours.py`를 실행하여 네이버 지도의 장소 검색 및 상세 정보(영업시간, 주소 등) 추출 담당

이 둘을 조합하여 **"Toss POS 페어링 ➡️ POS 정보 획득 ➡️ 네이버 검색/크롤링 ➡️ 상세 정보 병합 ➡️ DB 저장"** 의 자동화 파이프라인을 구축합니다.

---

## 2. 1단계: 온보딩(Onboarding) 및 매장 등록 파이프라인

사장님이 서비스에 가입하고 본인의 Toss POS 기기를 연동하여 최초의 매장 정보를 세팅하는 실시간 프로세스입니다.

### [진행 순서]
1. **TV 코드 기반 페어링 (POS ↔ BE ↔ 모바일)**
   * **[POS 단말기]**: 자체 생성한 6자리 난수(PIN)와 자신의 `merchant_id`를 백엔드에 전송합니다. 백엔드는 이를 임시 저장소(Redis)에 3분간 보관합니다.
   * **[모바일/웹]**: 사장님이 화면에 뜬 6자리 PIN을 입력하여 백엔드로 전송합니다. 백엔드는 PIN을 검증하고, 매칭된 `merchant_id`를 반환하며 기기 페어링을 완료합니다.

2. **Toss OpenAPI 호출 (가본 정보 및 메뉴 획득)**
   * 백엔드는 페어링된 `merchant_id`와 개발자 마스터 키(`x-access-key` 등)를 이용해 Toss OpenAPI를 호출합니다.
   * **이 단계에서 획득하여 DB에 저장할 주요 타겟 데이터:**
     * **사업장 정보:** 사업자/가맹점 번호(`merchant_id`), 가게 상호명(`store_name`), 가게 카테고리(`category`)
     * **메뉴 정보:** 메뉴 이름(`name`), 가격(`price`), 설명(`description`)

3. **네이버 지도 크롤러 호출 (장소 검색)**
   * 백엔드는 위에서 얻은 `store_name`을 키워드로 삼아 내부 FastAPI 크롤러에 장소 검색을 요청합니다. (`GET /api/search?keyword={store_name}`)
   * 크롤러로부터 매칭되는 후보 리스트 중 가장 정확한 네이버 지도의 `place_id`를 획득합니다. (동명이인 방지를 위해 프론트엔드에서 사장님께 직접 선택을 요청하는 UI 구현을 권장합니다.)

4. **상세 메타데이터 수집 (추가 정보 확보)**
   * 확정된 `place_id`를 이용해 다시 크롤러에 상세 조회를 요청합니다. (`GET /api/place/{place_id}`)
   * **이 단계에서 획득하여 DB에 보완/저장할 주요 타겟 데이터:**
     * **사업장 추가 정보:** 상세 주소(`address`), 위도(`latitude`), 경도(`longitude`)
     * **영업시간 정보:** 요일별 오픈/마감 시간 (`store_hours` 테이블 전체)

5. **데이터 병합 및 DB 최종 저장**
   * 백엔드(JPA)를 통해 `stores`, `store_hours`, `menus` 테이블에 획득한 모든 데이터를 역할에 맞게 분배하여 영구 저장(INSERT/UPDATE)합니다.

---

## 3. 2단계: Toss POS 통계 자료 수집 (배치 처리 시스템)

매장의 일간/주간 매출, 주문 건수 등의 통계 데이터를 가져오기 위해 정기적으로 실행되는 **배치(Batch) 프로세스**입니다. 매번 실시간으로 가져오면 API 제한이나 속도 문제가 생길 수 있으므로, 주로 새벽 시간에 백그라운드에서 동작하도록 설계합니다.

### [구현 계획]
1. **배치 스케줄러(Scheduler) 구성**
   * Spring Boot의 `@Scheduled` 어노테이션이나 **Spring Batch** 프레임워크를 도입합니다.
   * 예: 매일 새벽 3시에 전일자 통계 데이터를 수집하는 Job 생성.

2. **대상 매장 조회 및 Toss API 호출**
   * `stores` 테이블을 조회하여 Toss POS가 연동된(`merchant_id`가 있는) 매장 목록을 가져옵니다.
   * 각 매장의 인증 토큰을 이용해 Toss POS의 매출/통계 API(`/v1/sales`, `/v1/orders/stats` 등)를 순차적(또는 비동기 병렬)으로 호출합니다.

3. **데이터 가공 및 적재**
   * 가져온 원시 데이터(Raw Data)를 우리 서비스에 맞는 형태(예: 총 도달수 대비 구매 전환율, 시간대별 주문 피크 타임 등)로 가공합니다.
   * 기존 DB의 통계 전용 테이블(예: `account_weekly_metrics` 또는 신규 테이블 `toss_sales_metrics`)에 적재(Upsert)합니다.

4. **오류 처리 및 재시도 (Retry)**
   * Toss POS 서버 점검이나 네트워크 오류로 통계 수집에 실패할 경우를 대비해, 실패한 매장만 모아서 1시간 뒤에 다시 시도(Retry)하는 로직을 반드시 추가해야 합니다.

---

## 4. 요약: 백엔드 개발자가 구현해야 할 API 목록

1. `POST /api/v1/onboarding/pin/register`
   * POS 단말기에서 PIN과 `merchant_id`를 임시 등록(Redis)하는 API.
2. `POST /api/v1/onboarding/pin/verify`
   * 모바일/웹에서 PIN을 입력하여 페어링을 완료하고 `merchant_id`를 반환받는 API.
3. `POST /api/v1/stores/sync`
   * 페어링 완료 후, **(Toss 연동 -> 기본정보/메뉴 추출 -> 크롤러 검색/상세 추출 -> DB 영구 저장)** 의 전체 흐름을 일괄 처리하는 **Orchestration API** 역할.
4. `@Scheduled(cron = "0 0 3 * * *")` (통계 수집 스케줄러)
   * 새벽 3시마다 Toss API를 찌르고 DB를 업데이트하는 백그라운드 메서드.
