# 토스플레이스 OpenAPI 연동 및 페어링 인증 개념 정리

본 문서는 토스 POS 플러그인과 외부 서버(모바일 앱 등) 간의 인증 및 데이터 연동 과정에서 초기에 혼동했던 개념과, 최종적으로 올바르게 확립한 아키텍처(TV 코드 기반 페어링)를 비교하여 정리한 문서입니다.

---

## 💡 1. 초기에 혼동했던 개념 (Misconceptions)

- **API Key의 발급 주체 오해**
  - `x-access-key`와 `x-secret-key` 같은 OpenAPI 통신용 보안 키를 **각 사장님(가맹점)마다 개별적으로 발급**받아야 한다고 생각했습니다.
  - 혹은 POS 단말기(프론트엔드 플러그인) 내부에서 SDK를 통해 이 키들을 실시간으로 추출해 내야 한다고 오해했습니다.

- **토큰(Token)의 위치에 대한 오해**
  - 플러그인 프론트엔드(React)에서 `sdk.getAccessToken()`과 같은 방식으로 직접 토큰을 얻어내어 백엔드로 전달해야만 OpenAPI 호출이 가능하다고 생각했습니다.

- **사용자(사장님)의 인증 부담**
  - 외부 앱과 POS를 연동하기 위해 사장님이 직접 복잡한 인증 키를 복사/붙여넣기 하거나 번거로운 로그인 절차를 거쳐야 한다고 생각했습니다.

---

## 🎯 2. 올바르게 이해한 개념 (Corrected Concepts)

### ① 보안 키(API Key)는 "개발사 전용 마스터 키"로 숨겨서 관리한다
- `x-access-key`와 `x-secret-key`는 개발자가 **개발자 센터에서 딱 한 번 발급받는 고유한 '마스터 키'**입니다.
- 이 키는 절대 프론트엔드(POS 플러그인)로 노출시키지 않으며, 오직 **백엔드 서버의 환경 변수(`.env`)에 안전하게 숨겨서 관리**합니다.

### ② 프론트엔드(POS 플러그인)의 역할은 오직 "식별"뿐이다
- POS 단말기 안에서 도는 플러그인 코드는 보안 키를 알 필요가 없습니다. 
- 단지 SDK를 통해 **"내가 지금 설치된 가맹점 번호(`merchantId`)"**만 알아내고, 무작위로 생성한 **"6자리 난수"**와 함께 백엔드에 몰래 전달해 두는 역할만 합니다.

### ③ 6자리 난수(PIN)의 진짜 역할: "TV 코드 페어링 (Device Flow)"
- 난수 자체에는 보안 정보가 없습니다. 난수의 역할은 **POS 단말기(`merchantId`)와 사장님의 스마트폰(외부 클라이언트)을 묶어주는 '임시 연결고리'**입니다.
- **[동작 원리]**
  1. POS 화면에 `193001`이라는 난수가 뜹니다. (백엔드에는 `193001 = 가맹점A` 라고 임시 저장됨)
  2. 사장님은 본인의 스마트폰 앱에서 `193001`만 입력합니다.
  3. 백엔드는 난수를 확인하고 *"이 스마트폰을 쓰는 사람이 가맹점A의 사장님이구나!"* 라고 매핑(페어링)을 완료합니다.

### ④ OpenAPI 호출은 "백엔드"가 대리 수행한다
- 매핑이 완료되면, 백엔드 서버는 본인이 몰래 쥐고 있던 **'마스터 키(환경변수)'**와 방금 알아낸 **'가맹점 ID(`merchantId`)'**를 조합하여 토스 OpenAPI에 데이터를 요청합니다.
- 토스 서버는 *"정상적인 개발사 키(O) + 해당 가맹점이 이 개발사 앱 설치에 동의함(O)"*을 확인하고 데이터를 내어줍니다.

## 🚀 3. 비즈니스 / UX 관점의 결론 및 기대 효과

이러한 **TV 코드 기반 페어링 인증 방식**을 도입함으로써 얻는 가장 큰 수확은 **"압도적인 사용자 편의성(UX)"**입니다.

- 복잡한 IT 기술이나 회원가입 절차에 피로감을 느끼는 **시니어 사장님(디지털 소외 계층)들조차**, 마치 스마트 TV에 넷플릭스를 연결하듯 **"눈앞에 보이는 6자리 숫자만 치면 즉시 내 매장이 연동"**되는 마법 같은 온보딩(Onboarding) 경험을 제공할 수 있습니다. 
- 이는 해커톤이나 서비스 피칭 시 **기술적 보안성(키 은닉)과 사용자 친화적 UX를 동시에 달성한 훌륭한 설계 포인트**로 강력하게 어필할 수 있습니다.
