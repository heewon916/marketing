# GitLab clone 이후 빌드 및 배포 가이드

## 1. 시스템 개요

이 문서는 GitLab 소스 클론 이후 빌드 및 배포가 가능하도록 현재 저장소 기준의 서버 구성, 사용 기술, 환경 변수, 배포 특이사항, 주요 설정 파일 위치를 정리한 문서다.

- 기준 서버 구분
  - 기본 서버: `nginx`, `spring`, `frontend`, `fastapi`, `crawler`, `postgres`, `redis`
  - GPU 서버: `exaone-vllm`, `vlm-server`, `redis`
- 구성 기준 파일
  - 기본 서버: `compose.yaml`, `common/Jenkinsfile`, `nginx/`, `be/`, `fe/`, `ai/`, `crawler/`
  - GPU 서버: `gpu-server/docker-compose.yaml`
- 서버 연계 방식
  - 기본 서버의 `fastapi` 컨테이너는 GPU 서버 내부 모델 컨테이너를 직접 포함하지 않는다.
  - 대신 `KEYWORD_MODEL_BASE_URL`, `CAPTION_MODEL_BASE_URL`, `FINAL_EDIT_MODEL_BASE_URL` 등을 통해 외부 GPU 서버의 모델 API를 호출한다.

### 1-1. 기본 서버 역할

| 구성 요소 | 역할 |
| --- | --- |
| `nginx` | 80/443 진입점, HTTPS 처리, `spring`/`fastapi`/`frontend` 리버스 프록시 |
| `spring` | 메인 백엔드 API, 인증, DB/Redis 연동, 외부 API 연동 |
| `frontend` | React/Vite 기반 정적 프론트엔드 |
| `fastapi` | AI 관련 API, 모델 서버 호출, 이미지/텍스트 후처리 |
| `crawler` | 별도 FastAPI 기반 크롤링 서비스 |
| `postgres` | 메인 RDBMS |
| `redis` | 캐시 및 토큰/상태 저장용 인메모리 저장소 |

### 1-2. GPU 서버 역할

| 구성 요소 | 역할 |
| --- | --- |
| `exaone-vllm` | 텍스트 생성 계열 모델 서버 |
| `vlm-server` | 비전-언어 모델 서버 |
| `redis` | GPU 서버 내 캐시 및 보조 저장소 |

### 2-3. 네트워크 및 프록시 설정

- `nginx`는 80 포트 요청을 443 HTTPS로 리다이렉트한다.
- `/api/`는 `spring:8080`으로 프록시한다.
- `/ai/`, `/ai/docs`, `/ai/openapi.json`은 `fastapi:8000`으로 프록시한다.
- `/`는 `frontend:80`으로 프록시한다.
- SSL 인증서는 호스트의 `/etc/letsencrypt`를 읽기 전용으로 마운트한다.

## 4. 배포 시 특이사항

### 4-1. Jenkins 배포 절차

- Jenkins는 `common/Jenkinsfile` 기준으로 동작한다.
- 배포 대상 작업 디렉터리는 `/home/ubuntu/deploy/S14P31A401`이다.
- 이전 커밋 대비 변경 파일을 기준으로 재빌드 대상을 계산한다.
  - `compose.yaml` 또는 `common/Jenkinsfile`이 바뀌면 `spring`, `frontend`, `nginx`, `fastapi`, `crawler`를 모두 재빌드한다.
  - 그 외에는 폴더 단위 변경 감지로 일부 서비스만 재빌드한다.
- 배포 디렉터리 복사 시 아래 항목은 제외된다.
  - `.git`
  - `node_modules`
  - `dist`
  - `build`
  - `.gradle`
  - `.pnpm-store`
  - 루트 `.env`
  - `secrets`
  - Firebase 서비스 계정 JSON

### 4-2. 비밀정보 주입 방식

- Jenkins는 Secret File 자격 증명을 사용해 실제 `.env`를 배포 서버에 생성한다.
- Firebase 서비스 계정 JSON도 Jenkins Secret File로 별도 주입한다.
- 문서에 실제 `.env` 값이나 서비스 계정 JSON 본문을 기재하면 안 된다.
- 실제 민감 파일은 비공개로 취급한다.
- 루트 `.env`: 비공개
- `gpu-server/.env`: 비공개
- `secrets/firebase-service-account.json`: 비공개
- Let’s Encrypt 인증서 파일: 비공개

### 4-3. 환경 변수 검증 규칙

- Jenkins는 `.env` 파일에 대해 다음을 검증한다.
  - 파일 존재 여부
  - CRLF 포함 여부
  - 중복 키 존재 여부
  - 필수 키 누락 여부
  - `changeme`, `TODO`, `undefined` 등 플레이스홀더 값 사용 여부
- `FIREBASE_ENABLED`는 배포 시 `true`여야 한다.
- `CLOUDFRONT_DOMAIN`은 프로토콜 없이 도메인 형식만 허용한다.

### 4-4. Compose 및 컨테이너 배포 특이사항

- Jenkins는 `docker compose config`로 유효성을 검사하지만, 환경 변수 값이 펼쳐져 노출될 수 있으므로 결과 원문은 로그나 문서에 남기지 않는다.
- 최초 배포 또는 이미지 부재 시에는 Git 변경 여부와 무관하게 필요한 이미지 재빌드를 수행한다.
- 배포 중 `postgres`, `redis`를 먼저 기동한 뒤 애플리케이션 컨테이너를 교체한다.
- 최종 단계에서 `--remove-orphans`로 누락된 컨테이너 상태를 정리한다.
- 배포 완료 후 이미지 라벨의 `org.opencontainers.image.revision`으로 배포 커밋을 추적한다.

### 4-5. Health Check 및 운영 주의사항

- 기본 서버 Health Check 대상
  - `nginx` 응답 확인
  - `spring`의 `/api/health`
  - `fastapi`의 `/ai/health`
- GPU 서버 모델 Health Check는 현재 기본 서버 Jenkins 파이프라인에서 직접 수행하지 않는다.
- 따라서 GPU 서버 운영 시에는 별도 서버에서 모델 헬스 상태를 확인해야 한다.
- `nginx` 설정 검증은 `docker exec project-nginx nginx -t`로 수행한다.
- SSL 인증서 경로는 호스트의 `/etc/letsencrypt`를 마운트해 사용한다.
- 기본 서버의 `compose.yaml`에는 과거 단일 호스트용 모델 서버 블록이 주석으로 남아 있으므로, 현재 문서는 반드시 `gpu-server/docker-compose.yaml`을 기준으로 해석한다.
